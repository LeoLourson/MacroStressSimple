# Архитектура кейса

Три локальных процесса: PostgreSQL, один FastAPI worker и Streamlit.
MCP работает внутри API через транспорт FastMCP Client; отдельного сервиса MCP нет.

## Зависимости

```text
ui/app.py → HTTP → api.py → workflow.py
                             ├─ agents.py → llm/
                             ├─ mcp.py → engine/ → assets/
                             └─ db/
reporting.py → факты расчёта и проверенные ссылки рекомендаций
```

В `assets/` находятся финансовые поля, формулы, подписи и правила агрегации.
`engine/` работает с декларациями и массивами без ветвления по типам активов.
UI получает названия и единицы из `GET /v1/asset-types`.

## Пять этапов

1. `scenario`: MCP get_portfolio, LLM-сценарий, проверка драйверов и дословной цитаты.
2. `review`: LangGraph interrupt; человек подтверждает/меняет сценарий.
3. `calculate`: MCP run_calculation; результат сохраняется до запроса рекомендаций.
4. `recommendations`: модель вызывает MCP get_calculation_results, получает факты,
   возвращает рекомендации с evidence. Проверяются ссылки и отсутствие цифр в прозе.
5. `approval`: LangGraph interrupt; человек утверждает или отклоняет отчёт.

Состояние графа — идентификатор запуска. Большие результаты хранятся в SQLAlchemy-снимке.
Успешные этапы фиксируются чекпоинтами. После ошибки можно повторить незавершённый этап.
При сбое между записью прикладного результата и чекпоинта этап может выполниться повторно:
гарантии exactly-once для внешних LLM-запросов нет.

## Хранение

- `portfolio`: один синтетический портфель.
- `run`: запрос, снимок исходного портфеля, сценарий, подтверждения, результат,
  рекомендации, профиль модели, трасса MCP и статус.
- `alembic_version`: независимая история миграций схемы.
- `checkpoints`: схема PostgreSQL для таблиц LangGraph.

База запуска — `msa_product`. Старые базы и таблицы не удаляются.
SQLite и SQLite-чекпоинты служат для изолированных тестов.

HTTP-запрос ожидает выполнения этапов до следующего `interrupt`.
Один `asyncio.Lock` исключает одновременные изменения внутри единственного worker.
Не поддерживаются распределённые worker, роли пользователей и очередь заданий.

## HTTP

| Метод | Путь | Назначение |
|---|---|---|
| GET | /health | Проверка запуска |
| GET | /v1/asset-types | Типы, поля, драйверы, метрики, допущения |
| GET | /v1/demo | Портфель, события и профиль LLM |
| GET/POST | /v1/runs | Последние запуски / создание |
| GET | /v1/runs/{id} | Снимок запуска и факты |
| POST | /v1/runs/{id}/confirm | Подтверждение сценария |
| POST | /v1/runs/{id}/decision | Утверждение/отклонение |
| POST | /v1/runs/{id}/retry | Повтор незавершённого этапа |
| GET | /v1/runs/{id}/report | Утверждённый Markdown-отчёт |

## Граница LLM/MCP

Первый запрос рекомендаций содержит инструкции и схему инструмента, без результатов расчёта.
Вызов `get_calculation_results` обязателен. Сервер привязан к `run_id` замыканием;
аргументы отсутствуют, читать другой запуск нельзя.
Второй запрос содержит assistant tool_call и соответствующее tool-сообщение с результатом.
Модели не выдаются инструменты изменения состояния или подтверждения отчёта.

Выгрузка фактов включает все P5/P50/P95, базу, вероятность нарушения, описания метрик,
допущения и хеш матрицы. Текст рекомендации не считается подтверждением корректности вывода.
